# Project 10 — Restaurant Orders & Menu Performance Analyzer

## 1. Project Overview

This project was developed for the **Programming Techniques** course as a Python application designed to analyze restaurant orders and menu performance.

The application combines two CSV datasets containing menu information and customer order records. By matching orders to menu items, it provides insights into sales volume, revenue, estimated costs, gross margins, and menu-item profitability.

The main objective is to help restaurant management understand product performance, identify demand patterns, evaluate hypothetical pricing scenarios, and generate recommendations for menu optimization.

In addition to the core analysis, the application includes synthetic order generation, detailed temporal analysis, graphical dashboards, hypothetical price simulations, and rule-based menu recommendations.

The main analytical calculations rely on fundamental Python programming concepts, including functions, loops, conditions, dictionaries, lists, and sorting. Pandas and Matplotlib are used to complement these calculations through data organization and visualization.

### 4.1. Application Execution Flow

The application follows a structured sequence of operations coordinated by `main.py`.

1. **Data loading and validation:** The application reads the original menu and order files or generates synthetic orders when requested. Input records are validated, and invalid records are identified and reported.

2. **Order matching and financial calculations:** Valid orders are matched to menu items using `item_id`. The application calculates quantities sold, revenue, estimated costs, and gross margins at the item and category levels.

3. **Performance and temporal analysis:** Menu items are ranked according to sales volume and gross margin. Demand is also analyzed by time of day, weekday, and combined weekday/time-period intervals.

4. **Price simulation and recommendations:** The application generates rule-based recommendations for menu items and evaluates hypothetical price changes. A specific price-change scenario is calculated when requested through the command-line interface.

5. **Report generation and visualization:** The calculated results are organized into CSV files, a structured textual report, a graphical performance dashboard, and a price-sensitivity chart.

6. **Output storage:** The application saves the generated results in the `results/` directory, allowing users to inspect and compare restaurant performance indicators.

### 4.2. Design Principles

The project was developed using a modular structure to ensure that individual components can be understood, maintained, and tested independently.

The main analytical calculations are implemented primarily using fundamental Python constructs, including functions, loops, conditional statements, lists, dictionaries, and sorting operations.

External libraries such as Pandas and Matplotlib complement these calculations by supporting data preparation and graphical visualization rather than replacing the core analytical logic.

This separation of responsibilities also allows the application to reuse the same analytical functions when processing both the original course data and synthetically generated orders.

## 5. Installation and Execution

The application runs through the command-line interface (CLI), using `main.py` as its entry point. Users can analyze the original restaurant dataset, generate synthetic orders, and evaluate hypothetical price changes through configurable command-line arguments.

### 5.1. Prerequisites

Before running the application, ensure that the following are available:

- **Python 3**
- **pip**, Python's package installer
- **Pandas**, for DataFrame processing and analytical summaries
- **Matplotlib**, for graphical visualizations

The external dependencies are listed in the project's `requirements.txt` file.

To install them, open a terminal in the project's root directory and execute:

```bash
python -m pip install -r requirements.txt
```

On systems where Python 3 is accessed through `python3`, replace `python` with `python3` in the commands.

No additional external libraries are required. The remaining modules used by the application are part of Python's standard library.

### 5.2. Running the Original Dataset

To execute the application using the original course-provided datasets, run:

```bash
python main.py
```

This is equivalent to:

```bash
python main.py --mode original
```

The program reads:

- `data/menu.csv` — menu items, categories, prices, and estimated unit costs.
- `data/orders.csv` — customer order records, dates, times, item references, and quantities.

The application validates the inputs, matches orders to menu items, calculates performance indicators, generates rankings and recommendations, performs temporal analysis, and produces the corresponding reports and visualizations.

The results are saved automatically in the `results/` directory.

### 5.3. Generating Synthetic Orders (E02)

The application can also generate synthetic orders based on the existing menu.

To generate 500 order lines using a dinner-heavy demand profile and a fixed random seed, run:

```bash
python main.py --mode generated --num-orders 500 --profile dinner_heavy --seed 42
```

Three demand profiles are available:

| Profile | Description |
|---|---|
| `balanced` | Gives equal selection weight to lunch, afternoon, and dinner periods. |
| `lunch_heavy` | Assigns greater selection weight to the lunch period. |
| `dinner_heavy` | Assigns greater selection weight to the dinner period. |

Users can also configure the generation dates.

For example:

```bash
python main.py --mode generated --num-orders 1000 --profile lunch_heavy --seed 123 --start-date 2026-06-01 --num-days 30
```

This command generates 1,000 order lines over a period of 30 consecutive calendar days, starting on June 1, 2026.

The generated records follow the same five-column schema as the original `orders.csv` file. They use valid menu-item identifiers and can be processed by the same analytical functions.

A fixed random seed makes the generated dataset reproducible when the same menu and generation parameters are used.

### 5.4. Hypothetical Price Simulation (E05)

The application allows users to evaluate hypothetical percentage changes applied to all menu prices.

For example, to simulate a 10% price increase using the original dataset:

```bash
python main.py --mode original --price-change 10
```

To simulate a 15% price reduction:

```bash
python main.py --mode original --price-change -15
```

The simulation calculates new selling prices, revenue, and gross margins and compares them with the original results.

**Important assumption:** The quantities sold remain fixed throughout each hypothetical scenario. The simulation evaluates the financial impact of changing prices without assuming that customer demand increases or decreases.

Price changes below −100% are rejected, and the percentage must be a finite numerical value.

The application also generates a price-sensitivity chart comparing total gross margin across hypothetical menu-wide price changes from −50% to +50%, using increments of 10 percentage points.

### 5.5. Combining Synthetic Orders and Price Simulation

The order generator and price-simulation extension can also be used together.

For example:

```bash
python main.py --mode generated --num-orders 500 --profile dinner_heavy --seed 42 --price-change 10
```

This command:

1. Generates 500 synthetic order lines using the dinner-heavy profile.
2. Validates and analyzes the generated orders.
3. Calculates baseline menu performance and recommendations.
4. Simulates a 10% increase in menu prices while keeping generated quantities fixed.
5. Produces updated reports, CSV results, and graphical visualizations.

This demonstrates that the selected extensions are integrated into the same application.

### 6.6. Interpretation of Results

The application calculates financial performance using the following relationships:

- **Revenue:** Units sold × Selling price
- **Estimated cost:** Units sold × Estimated unit cost
- **Gross margin:** Revenue − Estimated cost
- **Gross margin percentage:** Gross margin ÷ Revenue × 100, when revenue is positive

Financial results are expressed in euros (EUR), while sales volumes and demand indicators are expressed in units or percentages, as appropriate.

The reported gross margins are based on the estimated costs supplied in the menu dataset and should not be interpreted as net profit after all restaurant operating expenses.

The generated reports and visualizations are designed to support comparisons between menu items, categories, demand periods, and hypothetical pricing scenarios.

Together, these outputs provide an interpretable overview of restaurant menu performance and support operational decision-making.

### 8.4. Main Analytical Assumptions

The application uses several explicit assumptions to keep its analytical models transparent and understandable.

**Estimated Unit Costs**

Financial calculations use the estimated `unit_cost` values supplied in the menu dataset. Gross margin represents revenue minus these estimated costs and does not account for all restaurant operating expenses.

**Synthetic Order Generation**

The generator creates order lines using valid menu-item identifiers, configurable time-of-day demand profiles, randomly selected quantities, and a user-defined random seed.

Menu items are selected with equal probability, while the selected demand profile controls the relative frequency of lunch, afternoon, and dinner orders. Generated quantities range from one to four units per order line.

The generator produces synthetic examples for analysis and testing, rather than predicting real customer behavior.

**Time-of-Day Classification**

Order timestamps are classified into five periods:

| Period | Time Interval |
|---|---|
| Morning | 00:00–11:59 |
| Lunch | 12:00–14:59 |
| Afternoon | 15:00–18:59 |
| Dinner | 19:00–22:59 |
| Late night | 23:00–23:59 |

These boundaries are used consistently throughout the temporal analysis.

**Hypothetical Price Changes**

Price simulations assume that observed sales quantities remain constant when menu prices change.

New prices are calculated using the specified percentage adjustment, and revenue and gross margins are recalculated accordingly.

The model does not estimate changes in customer demand caused by higher or lower prices.

**Rule-Based Recommendations**

Menu recommendations are determined using two indicators: units sold and gross margin percentage.

Demand is evaluated relative to the median units sold across menu items, while profitability is compared against a 55% gross-margin threshold.

Each item is classified as Maintain, Promote, Review, or Consider removal according to the documented decision rules.

These recommendations are analytical suggestions rather than automatic operational decisions.

### 8.5. Project Limitations

The application was designed as a structured educational project focused on fundamental programming techniques, data analysis, and transparent decision rules.

Its main limitations include:

- **Fixed-quantity price simulation:** The model does not incorporate price elasticity or changes in customer demand.
- **Estimated profitability:** Gross margins exclude other operating expenses, such as labor, rent, utilities, and taxes.
- **Simplified synthetic orders:** Generated order patterns are based on predefined probabilities and random selection rather than a model calibrated to real restaurant behavior.
- **Rule-based recommendations:** Menu classifications rely on explicit thresholds and do not incorporate customer preferences, ingredient availability, or predictive machine-learning models.
- **File-based operation:** Input and output data are managed through CSV, TXT, and PNG files instead of a database or graphical user interface.
- **Descriptive temporal analysis:** Demand comparisons describe the observed or generated datasets and are not forecasts of future restaurant activity.

These limitations are consistent with the project's intended scope and allow the underlying algorithms and calculations to remain interpretable and independently verifiable.
